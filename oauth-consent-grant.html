Incident Investigation Report, Illicit OAuth Consent Grant Simulation

Incident ID: INC-ICS-2026-0721-004 Related incidents: INC-ICS-2026-0716-001 (AiTM), INC-ICS-2026-0718-002 (BEC), TSA-ICS-2026-0721-003 (token control assessment). Both prior investigations checked for OAuth consent persistence and confirmed none existed. This exercise creates and investigates the mechanism those checks were looking for. Classification: Controlled detection-validation exercise (lab, self-generated telemetry, not a real breach) Attack type: Consent phishing / illicit OAuth grant MITRE: T1550.001 (Application Access Token), T1098.003 (Additional Cloud Credentials) Environment: iCustomerSolutions M365 E5 tenant, Microsoft Sentinel workspace law-sentinel-lab Application: M365 Document Verificatio, client ID e175816b-1d17-44f9-ab83-daea5fd1f7c2, service principal add4272e-64bd-4fab-8337-30e7518e2193 Date: 21 July 2026 Status: Closed. Grant revoked, service principal removed. Times: UTC throughout (captured in ET, ET + 4h)

1. Executive Summary

On 21 July 2026 a controlled consent-phishing exercise was performed to generate and investigate an illicit OAuth grant, the persistence mechanism that survives password reset, token revocation, and MFA re-registration. An application named to appear legitimate was registered and configured to request Mail.Read. An initial attempt to obtain consent from a standard user was blocked by the tenant's user consent policy, which routed the request to administrator approval. The policy was then deliberately relaxed and consent was granted at administrator level, producing a grant with ConsentType: AllPrincipals, meaning the application was pre-authorised for every user in the tenant rather than a single mailbox. The grant was revoked and the service principal deleted within 22 minutes. No data was accessed, as the application had no code and made no API calls. The exercise produced two findings of operational value: the tenant's default consent controls worked as designed and are the most effective preventive control available, and a single consent action generates three distinct audit operations, only one of which carries the permission detail that determines blast radius.

4. Key Finding: AllPrincipals is a third permission scope

Standard guidance presents the OAuth permission model as a binary: delegated permissions are scoped to one consenting user, application permissions grant tenant-wide access and always require admin approval. The evidence from this exercise shows that framing is incomplete.

The grant recorded here is delegated (IsAppOnly: False), which by the binary framing should mean single-user scope. But DelegatedPermissionGrant.ConsentType is AllPrincipals, which pre-authorises the application for every user in the tenant. No user will ever see a consent prompt for this application again. Any user who signs into it operates immediately with Mail.Read against their own mailbox.

The accurate blast radius is therefore neither "one mailbox" nor "unconditional access to all mailboxes". It is any user who signs into the application, with no further prompting. This sits between the two categories the binary model describes.

Why the escalation occurred. Had the standard user consented directly, ConsentType would have recorded as Principal with that user's object ID, scoping the grant to a single mailbox. Because consent was granted at administrator level, the grant escalated to tenant-wide. This is the concrete mechanism behind the general warning that a compromised administrator account is the high-value target in consent phishing.

Investigative implication. DelegatedPermissionGrant.ConsentType must be read on every consent investigation. An analyst who confirms only that permissions were delegated, and stops there, will materially under-scope the incident.

5. Second Finding: one consent action, three audit operations

A single consent generated three separate operations at 20:08:08:

Operation Category Target Carries
Consent to application ApplicationManagement The application Consent context: IsAdminConsent, IsAppOnly, OnBehalfOfAll
Add delegated permission grant ApplicationManagement Microsoft Graph Scope and ConsentType, the blast-radius detail
Add app role assignment grant to user UserManagement The application Assignment record

Detection guidance commonly keys only on Consent to application. That operation confirms a consent occurred but does not carry the permission scope or the consent type. The operation that does, Add delegated permission grant, targets Microsoft Graph rather than the malicious application, so a rule filtering on suspicious application names would miss it entirely.

A detection rule for illicit consent should therefore correlate both operations on timestamp and actor, rather than alerting on either alone.

6. Third Finding: preventive control operated correctly, and policy weakening is itself auditable

The default control worked. The initial consent attempt by a standard user was blocked. The tenant was configured with Microsoft-managed consent settings, under which user consent is permitted only for low-impact permissions from verified publishers or popular mail clients. Mail.Read for an unverified, newly registered application fell outside that scope, so Entra ID routed the request to administrator approval rather than presenting an accept prompt. No grant was created.

This is the single most effective preventive control against consent phishing, because the consent prompt itself is genuine Microsoft UI and offers users no visual means of distinguishing a malicious application from a legitimate one. User training cannot close that gap; removing the ability to consent does.

Weakening the control is detectable. The policy change at 20:00:18 generated Update authorization policy alongside Update role and Add role from template, because consent settings are enforced through default user role permissions. In a real intrusion, an attacker who has compromised an administrator would need to weaken this policy before phishing users at scale. That preparatory step is auditable, and detecting it provides warning before any consent grant occurs.

7. Containment and Eradication

Order Action Time (UTC) Verification
1 Revoke delegated permission grant (Mail.Read) 20:26:27 Remove delegated permission grant recorded
2 Delete enterprise application and service principal 20:30:40 Remove service principal recorded
3 Restore tenant user consent policy Post-eradication Confirmed via portal state

Why partial revocation is insufficient. After revoking Mail.Read, the application still existed with a live service principal and a residual User.Read grant. User.Read is low risk in isolation, but the application object remaining in the tenant is the actual exposure: an actor controlling that registration can request additional scopes, and users already covered by an AllPrincipals grant will not be prompted again for anything within it. Eradication of an illicit consent means removing the application, not reducing its permissions.

Why user token revocation is irrelevant here. No user session containment was performed, and none would have helped. A consented application authenticates using its own client credentials against its own grant, on a token chain entirely separate from any user session. This is why the standard containment sequence of password reset, token revocation, and MFA re-registration leaves consent-based persistence fully intact, and why both prior investigations in this series explicitly queried for consent grants before declaring containment complete.

9. Limitations (lab boundaries)

  • Admin consent, not user consent. The intended user-consent path was blocked by tenant policy, and a subsequent attempt via the authorisation URL failed with an endpoint error that was not resolved. Consent was therefore granted at administrator level. This changes the actor from a tricked end user to an administrator, and produced a tenant-wide AllPrincipals grant rather than a single-user Principal grant. The deviation is recorded rather than presented as a user-consent incident, and it produced the report's principal finding.
  • Policy weakening was performed by the analyst. The consent policy change at 20:00:18 was a deliberate exercise step, not adversary activity. It is included in the timeline because it mirrors a genuine attacker technique and demonstrates that the step is auditable.
  • No data access occurred, and none could be traced. The application consisted of a registration only, with no code and no client secret in use. It never called Microsoft Graph, so AADServicePrincipalSignInLogs would contain no activity and the "what did the application access" investigation stage could not be exercised. In a real incident this stage determines the data exposure scope and would be central to the report.
  • Application registered in the tenant under investigation. A genuine consent-phishing application is registered in an external tenant controlled by the attacker. Publisher verification and cross-tenant indicators, which are real investigative signals, are therefore absent here.
  • Single-tenant scale. Tenant-wide consent audit techniques were exercised against a tenant containing one application, so the technique is demonstrated but not stress-tested.

10. Note on query construction

An initial search for the consent event using where OperationName has "onsent" returned no results despite the event being present. The has operator in KQL matches whole indexed terms rather than substrings, so a partial word never matches. contains performs substring matching, and has "Consent" would have matched correctly.

The distinction has both correctness and performance consequences: has is term-indexed and efficient, contains scans and is slower. Using has with a partial term produces silent false negatives, which in an investigation is worse than an error, because an empty result reads as an absence of evidence.
