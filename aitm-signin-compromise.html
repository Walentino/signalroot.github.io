Incident Investigation Report — AiTM Credential-Phishing Simulation

Incident ID: INC-ICS-2026-0716-001 Classification: Controlled detection-validation exercise (lab, self-generated telemetry — not a real breach) Attack type: Adversary-in-the-Middle (AiTM) — post-compromise segment Environment: iCustomerSolutions M365 E5 tenant · Microsoft Sentinel workspace law-sentinel-lab · Defender XDR unified portal Affected account: dave@iCustomerSolutions.onmicrosoft.com (single test account) Investigation date: 16 July 2026 Status: Closed — contained and eradicated; detection methodology validated Times: UTC throughout (source events captured in ET; ET + 4h)

1. Executive Summary

On 16 July 2026, a controlled adversary-in-the-middle (AiTM) detection-validation exercise was performed against a single test account in the iCustomerSolutions M365 E5 tenant. The simulated adversary authenticated successfully from anonymized Tor infrastructure across four countries, with Entra ID Protection flagging the sign-ins as risky ("anonymous IP address") while Conditional Access did not evaluate them (notApplied). From a German Tor exit the actor read two mailbox items via proxy and created a mail-hiding inbox rule ("system") for persistence. The account was contained by 15:53 UTC through full session and refresh-token revocation, and the persistence rule was eradicated by 16:15 UTC, with mailbox forwarding, MFA-method registration, OAuth consent, and device registration all verified absent. No real data was exposed. The exercise validated the AiTM detection and investigation methodology end to end and surfaced a tenant telemetry gap (empty CloudAppEvents; OfficeActivity used as the working source). Hardening recommendations are in Section 7.

6. Root Cause

In this exercise the anomalous, risky sign-ins succeeded and were not challenged because no Conditional Access policy was scoped to the account — every risky sign-in recorded ConditionalAccessStatus = notApplied, meaning no policy evaluated the request. Contributing factors mirror the general AiTM root cause: no token binding (Conditional Access token protection) was configured, and no phishing-resistant (FIDO2) authentication was enforced, so an authenticated session from anonymized infrastructure faced no additional control.

Note on notApplied: in a production tenant, notApplied on a risky sign-in is itself a finding — it means no policy ran and warrants investigation. Here the cause is simply an unscoped policy set in a lab, not evidence of token replay. This report does not claim token replay: the evidence shows anomalous authenticated access from anonymizer infrastructure, not a captured legitimate-then-replayed session pair.

7. Recommendations

# Control What it prevents Cost Priority
1 Conditional Access token protection (token binding) Binds the session token to the originating device; a token used from a different device is rejected. The definitive AiTM preventive control. $0 (included in E5); ~hours of config High
2 Risk-based Conditional Access policy (block or require reauth on medium/high sign-in risk; block anonymous-IP sign-ins) Directly addresses the notApplied gap found here — anonymous-IP / risky sign-ins would be challenged or blocked. $0 (E5 / Entra ID P2) High
3 FIDO2 phishing-resistant MFA The credential is bound to the legitimate domain; an AiTM proxy on a look-alike domain cannot satisfy the challenge. Hardware/platform keys; rollout effort Medium
4 Continuous Access Evaluation (CAE) with strict enforcement Near-real-time token revocation on risk events (IP/location change, disable), shrinking the window a stolen token stays usable. $0 (E5) Medium
5 Inbox-rule / mail-flow monitoring Detection for New-InboxRule with move-to-hidden-folder or delete actions on finance/security keywords — the persistence pattern seen here. $0 (analytics rule) Medium

8.4 Limitations (lab-reality boundaries)

This exercise reproduced the post-compromise segment of an AiTM attack. The following were not present and are honestly excluded from findings:

  • No phishing lure / URL click. No real AiTM proxy was run; EmailEvents / UrlClickEvents carry no lure. The email-analysis and click-correlation steps were read-along only.
  • No token-replay pair. There is no legitimate-then-replayed sign-in sequence. Evidence is anomalous authenticated access from anonymizer IPs, not proven token replay.
  • No non-interactive token activity. AADNonInteractiveUserSignInLogs returned no attacker-IP rows — consistent with human interactive access via Tor, not scripted token abuse. A real case would show sustained Graph/EWS/OWA token calls here.
  • Single account, lab mailbox. No lateral spread, no waves, no real data exposure.
  • Telemetry gap surfaced. CloudAppEvents was empty in this tenant; post-compromise evidence was obtained from OfficeActivity after enabling the Microsoft 365 connector.
