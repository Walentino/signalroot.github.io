Token Security Control Assessment

Reference: TSA-ICS-2026-0721-003 Related incidents: INC-ICS-2026-0716-001 (AiTM credential phishing), INC-ICS-2026-0718-002 (BEC). Both reports recommended token protection and Continuous Access Evaluation. This assessment evaluates whether those controls are deployable and in what order. Type: Control gap assessment, not an incident investigation. See Section 6 for why. Environment: iCustomerSolutions M365 E5 tenant, Microsoft Sentinel workspace law-sentinel-lab Date: 21 July 2026

1. Summary

Both prior incident reports recommended Conditional Access token protection and Continuous Access Evaluation as the controls that defeat token replay. This assessment tested whether either is deployable in the current tenant.

Token protection is not deployable. It requires Entra joined or hybrid joined Windows devices with TPM 2.0, and is currently limited to Windows desktop applications. A device landscape query returned zero managed devices: all sign-ins originate from unmanaged macOS and unmanaged Windows endpoints with no device trust type recorded. The tenant is at 0% eligibility against a recommended threshold of 80%.

CAE standard enforcement is already active, as it is enabled by default on E5. CAE strict location enforcement is deployable but currently ineffective, because strict mode evaluates client IP against Conditional Access location policies and named locations, and the tenant has neither. This is the same root cause identified in INC-ICS-2026-0716-001, where every risky sign-in recorded ConditionalAccessStatus = notApplied because no policy evaluated the request.

The gap is therefore not a missing advanced control. It is a missing Conditional Access baseline. Recommended sequence is in Section 5.

2. Why token controls matter, mechanism

Token replay bypasses MFA because MFA is an authentication control and replay is a session control attack. The attacker presents a token that already passed MFA, so no password check and no MFA challenge occurs. From the identity provider's perspective this is session continuation, not a new sign-in.

Token types and their behaviour under containment:

Token Lifetime Revocable Survives password reset
Access token 60 to 90 minutes Not directly, expires naturally, CAE can force re-evaluation Yes, until expiry
Refresh token Up to 90 days, sliding window Yes, Revoke-MgUserSignInSession Yes, until explicitly revoked
Session cookie Session, or persistent up to 90 days Yes, session revocation Yes, until revoked
Primary Refresh Token Device registration lifetime Yes, device deregistration Yes, tied to device not password

Operational consequence. Password reset alone does not contain a token-based compromise. The refresh token was issued before the password change and has an independent lifetime, so it continues to mint new access tokens. Containment requires password reset plus token revocation, and ideally CAE enforcement.

The revocation gap. Session revocation invalidates refresh tokens and session cookies, but access tokens already issued remain valid until natural expiry, up to 90 minutes, because the resource server validates the token signature locally and does not call back to the identity provider. CAE closes this gap by having CAE-aware resource servers subscribe to critical event notifications.

5. Recommended actions, in sequence

Sequence matters. Deploying the advanced controls before the baseline delivers little protection.

1. Define named locations. Register known and corporate IP ranges in Entra ID. Prerequisite for any location-aware policy and for CAE strict enforcement to have anything to evaluate against. Cost $0.

2. Create a break-glass emergency access account and exclude it from all Conditional Access policies. Standard practice before any CA deployment. Critical in a single-administrator tenant, where a misconfigured policy can cause complete lockout with no second account available to remediate. Cost $0.

3. Deploy a risk-based Conditional Access policy in report-only mode. Block or require reauthentication on medium and high sign-in risk, and on anonymous IP address sign-ins. This directly addresses the notApplied finding from INC-ICS-2026-0716-001: the Tor sign-ins would have been challenged rather than silently permitted. Run report-only, review the what-if results, then enforce. Cost $0, included in Entra ID P2.

4. Enable CAE strict location enforcement. Only meaningful once steps 1 and 3 are in place. Reduces the revocation gap and rejects tokens presented from locations the policy does not permit. Deploy report-only first. Cost $0.

5. Token protection, deferred. Not deployable in the current environment. Revisit only if the estate moves to Entra joined Windows devices with TPM 2.0. Note that the control is limited to Windows desktop applications and does not currently cover macOS, mobile, or browser sessions, so it would not have protected the browser-based activity observed in either prior incident even with managed devices.

Interim compensating control. Until token protection becomes viable, CAE strict enforcement plus risk-based Conditional Access is the primary defence against token replay. For BYOD-heavy or non-Windows estates this is the standard fallback position, not a workaround.

6. Scope and limitations

This assessment is deliberately not an incident investigation, and the reason is worth stating.

Generating a genuine token replay artefact requires capturing a live session token and replaying it from separate infrastructure, which means operating a functioning adversary-in-the-middle proxy. That was ruled out at the start of this lab work as unsafe and unnecessary. Without it there is no authentic replay evidence to investigate.

Two supporting findings confirm the boundary rather than working around it:

  • AADNonInteractiveUserSignInLogs, the primary evidence table for refresh token replay, returned no rows for the attacker IP during INC-ICS-2026-0716-001. The anonymised sign-ins in that incident were fresh authentications, not replays of a captured token.
  • Consequently INC-ICS-2026-0716-001 does not claim token replay. It claims anomalous authenticated access from anonymiser infrastructure, which is what the evidence supports.

Producing a fabricated token replay narrative would have been the alternative, and was rejected. An assessment that accurately reports what the environment can and cannot demonstrate is more defensible than an investigation of an event that did not occur.

Additional limitations. The device landscape sample covers a small lab tenant, so the 0% managed figure reflects the lab rather than a production estate. The blast radius assessments that would normally precede a Conditional Access deployment, such as measuring how many users legitimately sign in from three or more IP addresses, are not statistically meaningful at this scale. The methodology of measuring blast radius before enforcing is the transferable practice.

7. Corrections applied to prior reports

This assessment refines two points in the earlier incident reports.

Containment completeness, INC-ICS-2026-0716-001. Session revocation was performed at 15:53 UTC and was proportionate given that no MFA registration, OAuth consent, or device registration existed. However, access tokens issued before revocation remained valid until natural expiry, leaving a theoretical window of up to 90 minutes. Disabling the account would have triggered CAE re-evaluation and closed that window immediately. The decision to revoke without disabling optimised for minimal disruption; disabling optimises for speed of containment. Both are defensible, and the choice depends on confidence that the actor is no longer active.

Recommendation precision, both reports. Both reports listed token protection as a high priority control. Following this assessment, that recommendation is downgraded to deferred and platform-blocked, and risk-based Conditional Access is elevated to first priority, since it is deployable today and directly addresses the observed notApplied root cause.
